# Wanderly v1.9.1 Trip Package Integration Audit

审计日期：2026-07-19  
范围：只审计 Wanderly 主站如何接入 `trip_packages/` 已生成 Trip Package，不修改业务代码、不导入五城、不改 Content/Image Pipeline、不改 Trip Package Builder、不改数据库 schema、不改 Workspace 保存逻辑。

## 1. 结论摘要

当前 Wanderly 已经有三套相关数据层：

1. Explore 内容层：`ExploreTripContent`，来源混合为 normalized JSON、Supabase `explore_trip_contents`、mock fallback。
2. Workspace/Result 工作台层：`TripPlan` + `TripRequest`，主要从 `localStorage` 读取，保存时写入 Supabase `trip_plans`。
3. Explore 导入工作台桥接层：`TripPlanDraft`，由 `ExploreTripContent` 通过 adapter 转换成 Workspace 可打开的 `TripPlan` 草稿。

Trip Package 不应直接喂给 Workspace。推荐新增只读 package loader 与 adapter：

```text
Trip Package
  package_manifest.json
  content/explore_plan.json
  content/image_manifest.json
  images/files/*
  images/image_assets/*
        |
        v
Package Loader
        |
        v
Package -> ExploreTripContent Adapter
        |
        v
Existing Explore Reader / Detail / Import Flow
        |
        v
TripPlanDraft / TripPlan
        |
        v
Workspace / My Trips
```

这样可以最大化复用 v1.8.4 的登录、保存、My Trips、Settings、AI 偏好和 Workspace 链路，避免直接触碰数据库 schema 与保存逻辑。

### 2.5 图片加载方式

- `data/explore/normalized/explore_archive_image_manifest.json`

当前图片路径基本假设为 `/images/...`，也就是 Next.js `public/images` 下的静态资源。Explore 图片解析逻辑：

```text

  -> normalized image manifest cover
  -> /images/explore/cities/{city}-city-card.png
  -> /images/explore/archive/fallback/*
  -> /images/explore/fallback/*
```

Trip Package 的图片目前位于：

```text
trip_packages/{package_id}/images/files/*
trip_packages/{package_id}/images/image_assets/*.json
```

该目录不在 `public/` 下，不能直接用 `/images/...` URL 访问，也不能被当前 `ResolvedImage` 直接显示。

### 2.6 地图数据来源

相关文件：

- `hooks/useTripMap.ts`
- `lib/trip/enrichTripPlan.ts`
- `lib/trip/route-insight.ts`
- `app/api/enrich-trip/route.ts`
- `app/api/map/search/route.ts`
- `app/api/map/route-estimate/route.ts`
- `lib/poi/**`
- `lib/route/**`

地图不是来自 Explore 或 Trip Package 的坐标字段。当前逻辑从 `TripPlan.dailyItinerary` 中提取 `ItineraryItem.placeName`，再通过 POI Provider 搜索坐标，通过 Route Provider 估算路线。

因此 Trip Package 只要能转换出质量较好的 `placeName`，地图链路可以继续复用；若 package 后续提供坐标，当前模型没有字段承接，需要另行设计，但 v1.9 不建议改 schema。

### 2.7 当前混用情况

当前存在以下混用：

- Explore：normalized 静态 JSON + Supabase API + mock fallback。
- Workspace：localStorage 为当前编辑真实来源。
- My Trips：Supabase `trip_plans` 为云端保存来源。
- Explore 导入 Workspace：先写 localStorage，不立即写 Supabase。
- 图片：`public/images` 静态路径 + normalized image manifest fallback。
- 地图：从当前 `TripPlan` 动态抽取地点，再调用 POI/Route provider。

这是合理的 v1.8.4 过渡状态，但 v1.9 接 Trip Package 时需要收敛入口，避免再增加一条组件直接读文件的旁路。

## 7. 推荐接入方案

### 7.1 新增只读 package loader

建议新增：

```text
lib/trip-packages/types.ts
lib/trip-packages/schema.ts
lib/trip-packages/loader.ts
lib/trip-packages/to-explore.ts
lib/trip-packages/image-public-paths.ts
```

职责：

- 读取白名单 package id。
- 读取 `package_manifest.json`。
- 读取 `content/explore_plan.json`。
- 读取 `content/image_manifest.json`。
- 读取 `images/image_assets/*.json`。
- 读取 `validation/assembly_report.json`。
- 校验 `validation.status === "passed"`。
- 生成 `ExploreTripContent`。
- 生成 package image binding map。

注意：不要修改 Content Pipeline、Image Pipeline、Trip Package Builder。

### 7.2 图片访问策略

可选方案：

1. public 复制方案，推荐 v1.9.2 起步：

```text
trip_packages/beijing_couple_golden_v2/images/files/*
  -> public/images/trip-packages/beijing_couple_golden_v2/*
```

优点：

- 与当前 `/images/...` 体系一致。
- `ResolvedImage` 和 `next/image` 基本无需改。
- 适合静态 package 内容。

缺点：

- 需要构建/同步脚本。
- 图片有重复拷贝。

2. API image route 方案：

```text
/api/trip-packages/[packageId]/images/[file]
```

优点：

- 不复制文件。
- 可做权限/缓存/provenance。

缺点：

- 需要处理 `next/image` remote/local loader 配置。
- 较 public 方案复杂。

本阶段建议先采用 public 复制方案，后续如 package 规模扩大再考虑 API streaming。

### 7.3 Explore API 接入位置

推荐在 `/api/explore` 的 normalized JSON 前后加入 package source，但初期只接一个北京包时可以让 package 优先：

```text
Package ExploreTripContent
  -> normalized JSON
  -> Supabase
  -> mock fallback
```

原因：

- v1.9 的目标是新 Explore 计划文案 + 图片成果。
- package 是更高质量的新源，应优先于旧 normalized archive。

但要注意 slug 冲突。如果 package slug 与 normalized JSON slug 相同，需要明确优先级。

### 7.4 Workspace 导入策略

不要让 Workspace 直接读取 Trip Package。推荐：

```text
Trip Package
  -> ExploreTripContent
  -> normalizeExploreArchiveForReader()
  -> buildTripPlanDraftFromExplore()
  -> startExploreWorkspaceFlow()
  -> localStorage trip-plan
  -> /workspace
```

必要增强：

- `buildTripPlanDraftFromExplore()` 应尽量把 POI/food 名称解析成真实 `placeName`，而不是仅把 `poi_refs` id 当 placeName。
- 当前 `toItineraryItem()` 使用 `activity.poiRefs[0] ?? foodRefs[0]` 作为 `placeName`，会出现 `poi_forbidden_city` 这类 id，而不是中文地点名。v1.9 Workspace 精修时应通过 `pois/food` id map 转成展示名称。

### 7.5 provenance 与 validation 保留方式

不改 schema 的前提下，建议放入：

- `ExploreTripContent.source`
- `ExploreTripContent.rawContent.package`
- `ExploreTripContent.rawContent.validation`
- `ExploreTripContent.rawContent.imageBindings`

示例：

```ts
rawContent: {
  explorePlan,
  package: {
    packageId,
    packageVersion,
    generatedOn,
    sourceOutputs,
  },
  validation: {
    status,
    checks,
    counts,
    issues,
    warnings,
  },
  imageBindings,
}
```

这样 Explore detail 可以读，Workspace 导入也不会丢。

## 8. 风险点

### 8.1 Trip Package 与 TripPlan 字段不一致

风险：高。

Trip Package 的 `explore_plan.json` 是 Explore 内容模型，不是完整 `TripPlan`。缺少天气、住宿、交通、完整预算拆分等字段。

建议：

- 不直接喂 Workspace。
- 通过 adapter 生成 `TripPlanDraft`。
- 对缺失字段用明确保守文案兜底。
- 保持 “导入为草稿” 的产品语义。

### 8.2 POI refs 与 Workspace placeName 不一致

风险：高。

`daily_itinerary.activities[].poi_refs` 引用的是 `pois[].id`，例如 `poi_forbidden_city`。当前旧 adapter 容易把 id 当 `placeName`，会影响：

- Workspace 可读性。
- 地图 POI 搜索。
- 路线估算。
- 用户编辑体验。

建议：

- package adapter 构建 `poiById` 和 `foodById`。
- `ItineraryItem.placeName` 使用 `poi.name` 或 `food.name`。
- `matchedInterests` 可保留 id。
- `guide` 中可写 refs 和来源说明。

### 8.3 图片路径不能直接访问

风险：高。

`trip_packages/**/images/files/*` 不在 `public/` 下。当前 `ResolvedImage` 只接受可被浏览器访问的 URL。

建议：

- v1.9.2 北京包接入时同步图片到 `public/images/trip-packages/beijing_couple_golden_v2/`。
- adapter 输出 `/images/trip-packages/{package_id}/{filename}`。
- 保留原始 `packaged_file_path` 到 rawContent。

### 8.4 asset_instance_id 足够定位图片，但不足够完成内容绑定

风险：中高。

`asset_instance_id` 在 package 内唯一，足够定位图片实例；但 `explore_plan` 的 POI/food 使用 `poi_refs/food_refs`，并不直接引用 `asset_instance_id`。

建议绑定优先级：

1. 手工/规则映射：`poi.id/food.id -> asset_id/asset_instance_id`。
2. `asset_id` 与 inventory canonical asset id 对齐。
3. `asset_name` 与 `poi.name/food.name` 近似匹配。
4. `image_slot`/`image_usage_profile` 决定用途 fallback。

短期北京包可用规则：

- `explore_cover` -> Explore card/detail cover 候选。
- `day_cover` -> 对应 day 的氛围图候选。
- `poi_gallery` + `asset_name/asset_id` -> POI 图。
- `food_gallery` -> food 图。

### 8.5 normalized JSON 与 package slug/id 可能冲突

风险：中。

当前 `/api/explore/[id]` 会优先查 normalized slug/externalId。若 package 使用同 slug，可能仍返回旧 normalized 内容。

建议：

- Package source 优先级高于 normalized。
- 或使用 package-specific slug，例如 `beijing-couple-first-impression-v19`。
- `externalId` 推荐使用 package id，如 `beijing_couple_golden_v2`。

### 8.6 不应影响 v1.8.4 登录、保存、My Trips、Settings、AI 生成链路

风险：中，可控。

只要接入点停留在 Explore API 和 Explore adapter，不改：

- `trip_plans` schema
- `/api/trips`
- `lib/trips/save-payload.ts`
- `lib/trip/storage.ts`
- Settings/user_settings
- `/api/generate-trip`

则风险较低。

保存时仍以现有 `TripPlan` 为唯一真实来源，`source_type = explore_import` 即可。

### 8.7 package validation 不能只看 status

风险：中。

北京 Golden report 包含 `provenance_present`；上海/西安 assembly report 字段略少。不能假设每个 package 都有 `golden_review.json`。

建议：

- loader 容忍 `golden_review.json` 缺失。
- 必查 `assembly_report.status === "passed"`。
- 对 `issues.length > 0` 的 package 不进入默认 Explore。
- 对 `warnings` 保留到 rawContent。

### 8.8 图片授权与真实照片 provenance

风险：中。

`image_asset.metadata.license` 有 “verify exact license before public commercial use” 之类提示。上线前需要产品/法务确认真实照片授权范围。

建议：

- v1.9 详情页可先内部使用。
- 对 real_photo provenance 在 rawContent 保留完整 metadata。
- 后续如公开部署，应对 Wikimedia/Pexels source URL/license 建 review 清单。

## 11. 最终建议

v1.9 的正确接入点不是 Workspace，也不是数据库，而是 Explore 内容适配层。

推荐原则：

1. Trip Package 是新的上游内容源。
2. `ExploreTripContent` 是站内 Explore 统一模型。
3. `TripPlanDraft` 是 Explore 进入 Workspace 的桥。
4. `TripPlan` 仍是 Workspace 展示、编辑、复制、导出、保存的唯一真实来源。
5. 图片必须先变成浏览器可访问 URL，再进入现有 `ResolvedImage` 候选链。
6. provenance 与 validation 先保留到 `rawContent`，不急着改 schema。
